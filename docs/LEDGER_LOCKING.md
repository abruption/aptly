# 원장 잠금과 중단 후 복구 — 다음 버전 초안

이 문서는 [Issue #12](https://github.com/abruption/aptly/issues/12)의 개발 초안입니다. npm `0.1.1`에는 포함되지 않았으며, 이 문서 자체가 Linux·macOS·Windows 실기 검증 성공을 뜻하지 않습니다. 일반 사용 안내는 [한국어 가이드](guide/ko.md)를 참고하십시오.

## 보존하는 상태

추천 상태는 기존 JSON 원장에 그대로 저장합니다. 원장의 schema, 요청 ID와 digest, `unknown` 기록, 완료 캐시, 호출 수, 일별 카운터, 추정 비용 예약을 잠금 전환 때문에 초기화하지 않습니다. 분류 정책이나 모델·effort의 명시 선택도 바꾸지 않습니다.

잠금 소유자가 종료된 뒤 새 요청이 원장에 접근할 수 있게 하는 것이 목적입니다. 이전 요청의 결과가 불명확했다면 같은 ID는 계속 `outcome_unknown`이며, 새 ID로 자동 재호출하거나 예약 비용을 환불하지 않습니다. 완료된 결과는 기존 캐시 검증을 거쳐 재사용합니다. 잠금 복구는 실제 API 청구 결과를 확정하지 않습니다.

## 프로세스 수명에 따른 소유권

영속 원장을 사용하는 경로만 Node.js 24 내장 `node:sqlite`를 지연 로드합니다. 메모리 전용 fixture 경로는 SQLite나 잠금 파일을 필요로 하지 않습니다. Node.js의 SQLite API 설명은 [고정 버전 문서](https://nodejs.org/download/release/v24.22.1/docs/api/sqlite.html)를 참고하십시오.

JSON 원장 옆의 `ledger.json.lock`은 영구 SQLite 잠금 파일입니다. gate는 rollback journal의 `DELETE` 모드로 초기화하며 다른 journal 모드로 변경된 파일은 재설정하지 않고 거절합니다. 원장 읽기와 캐시 확인 전에 `BEGIN IMMEDIATE`를 획득하고, 예약 저장·제공자 대기·완료 저장이 끝날 때까지 연결을 유지합니다. 다른 writer가 소유하면 획득을 거절합니다. SQLite의 동시 write transaction 및 종료 규칙은 [공식 transaction 문서](https://www.sqlite.org/lang_transaction.html)에 설명되어 있습니다.

정상 해제에서는 transaction을 rollback하고 해당 연결을 닫습니다. 프로세스가 종료되면 OS 잠금이 해제됩니다. canonical `.lock` 경로를 unlink하거나 새 파일로 교체하지 않으므로, 이전 소유자의 정리가 후속 소유자의 잠금 파일을 지우는 경로를 만들지 않습니다. 잠금 파일이 남아 있다는 사실은 활성 소유자가 있다는 증거가 아닙니다. PID·파일 나이·타임아웃으로 소유자 종료를 추측하지 않습니다.

기존 `.lock`이 Aptly 고유 SQLite 형식인지 확인하고, 경로·파일 identity·권한 변경을 관측하면 원장 쓰기를 중단합니다. 활성 SQLite 연결이 있는 동안 같은 프로세스가 일반 파일 API로 gate 내용을 열고 닫아서는 안 됩니다. gate 내용 검사는 SQLite가 담당하고, 파일 identity 검사는 metadata로 제한합니다. [SQLite 잠금·파일 교체 주의사항](https://www.sqlite.org/howtocorrupt.html)을 참고하십시오.

## 초기화와 저장 임시 파일

처음 만드는 gate는 같은 비공개 디렉터리의 고유 임시 파일에 SQLite 형식과 Aptly 식별자를 완성하고 연결을 닫은 뒤, hard link로 canonical `.lock` 경로에 게시합니다. 대상이 이미 있으면 덮어쓰지 않습니다. canonical 파일이 만들어진 뒤 이 과정이 만든 초기화용 경로만 제거하고, 이후 SQLite는 canonical 경로만 엽니다.

초기화 중 프로세스가 종료되어도 canonical 경로에 미완성 gate를 게시하지 않습니다. 초기화용 경로만 남거나, 완성된 canonical gate와 비활성 초기화용 경로가 함께 남을 수 있습니다. 다른 요청은 이런 남은 임시 경로를 DB로 열거나 임의로 삭제하지 않습니다. 사용 중 gate의 별칭으로 열어서도 안 됩니다.

JSON 원장 저장용 임시 파일은 쓰기마다 고유 nonce를 사용합니다. 이전 프로세스가 남긴 임시 파일이나 재사용된 PID가 새 저장 경로를 차지하지 않도록 하며, 출처 불명의 과거 저장 임시 파일을 자동으로 정리하지 않습니다.

## 지원 범위

- JSON 원장과 gate는 비공개 디렉터리 안에 두고, 모든 writer가 하나의 canonical 경로를 사용해야 합니다. POSIX에서는 사용자 소유 디렉터리 `700`과 비공개 파일 권한을, Windows에서는 비공개 ACL을 유지합니다.
- 원자적 hard link와 SQLite 파일 잠금을 지원하는 로컬 파일시스템을 전제로 합니다. 네트워크 공유·NFS·클라우드 동기화 폴더·경로 별칭·다른 프로세스의 gate 교체는 지원 범위가 아닙니다. 지원하지 않는 초기화나 잠금 동작은 기존 파일을 덮어쓰는 방식으로 우회하지 않습니다.
- gate와 SQLite journal을 사용 중에 삭제·이동·교체·복사·복원하지 마십시오. 다른 SQLite 도구로 gate를 열어서도 안 됩니다. 외부 도구의 descriptor 처리나 파일 잠금 방식이 현재 소유권을 방해할 수 있습니다.
- 기존 `wx` 방식의 Aptly는 영구 `.lock`이 존재하면 접근하지 못합니다. 같은 원장에 접근하는 모든 writer를 함께 새 버전으로 전환하십시오. 구버전과 신버전의 혼합 운영은 지원하지 않습니다.
- 이 변경의 복구 범위는 프로세스 중단입니다. 전원 차단·저장장치 고장·파일시스템 손상·동시 외부 파일 편집에 대한 완전한 복구나 JSON과 원격 API 사이의 원자적 transaction을 보장하지 않습니다.

## 기존 빈 잠금의 보수적 오프라인 전환

예전의 빈 `.lock`은 소유자 정보가 없으므로 살아 있는 기존 writer와 중단된 프로세스의 흔적을 구분할 수 없습니다. 새 버전은 이런 파일이나 인식할 수 없는 형식을 자동으로 초기화·회수하지 않습니다. `ledger_locked`가 계속되더라도 시간을 기다리거나 PID만 확인한 뒤 삭제하는 방법으로 해결하지 마십시오.

운영자가 기존 잠금임을 확인한 경우 다음 순서로 전환합니다.

1. 해당 원장에 접근할 수 있는 모든 호스트, MCP 서버, 별도 CLI와 구버전 프로세스를 정지합니다. 관련 writer가 남지 않았음을 확인할 수 없다면 차단 상태를 유지합니다.
2. 중지된 상태에서 JSON 원장을 보존합니다. `unknown`, 완료 결과, 호출 수와 추정 비용을 지우거나 수정하지 않습니다.
3. 문제의 `.lock`이 기존 방식의 잠금임을 확인한 경우에만 운영자 판단으로 그 파일을 별도로 격리합니다. 새 SQLite gate나 journal에는 이 절차를 적용하지 않습니다. 형식이 불명확하면 조사부터 진행합니다.
4. 모든 writer를 새 버전으로 전환하고 원래 JSON 원장 경로로 다시 시작합니다. 잠금 회피를 위해 새 원장 경로나 새 요청 ID를 만들지 않습니다.
5. 기존 불명 요청은 `outcome_unknown`으로 유지되고, 새 요청의 예약과 완료 결과 처리가 재개되는지 확인합니다. 관측된 충돌·손상·불명 소유권은 자동 정리로 숨기지 않습니다.

오프라인 전환은 운영자가 모든 writer를 정지했다는 사실에 의존합니다. 프로그램이 기존 빈 잠금의 종료 소유권을 증명한 자동 복구와 같은 것으로 표현하지 않습니다. 실제 운영 원장·자격 정보를 합성 시험 데이터로 사용하지 마십시오.
