# Aptly 0.1.4 게시 및 provenance 검증

2026-11-06에 `aptly@0.1.4`를 GitHub Actions의 npm OIDC 경로로 게시하고 registry 파일과 provenance를 검증했습니다. 이 기록은 [Issue #65](https://github.com/abruption/aptly/issues/65)의 실제 게시 근거입니다. 변경 내용은 [한국어 릴리즈 노트](../release-notes/0.1.4.md), 일반적인 절차는 [배포 안내](../RELEASING.md)를 참고하십시오.

| 확인 항목 | 결과 |
|---|---|
| npm 게시 | 확인 완료 — `aptly@0.1.4`, 확인 당시 `latest=0.1.4` |
| registry 파일과 준비 artifact 일치 | 확인 완료 — SHA-256 및 SHA-512 integrity 일치 |
| npm 서명·provenance 검증 | 확인 완료 — 정확한 버전의 SLSA v1 bundle 확인 |
| 인증서 identity·소스·실행 연결 | 확인 완료 — GitHub CLI 검증 및 기대값 대조 |

릴리즈 준비의 회귀 테스트 432개를 통과했고, 태그를 생성하기 전에 [main CI 42202524221](https://github.com/abruption/aptly/actions/runs/42202524221)의 7개 job이 모두 성공했음을 확인했습니다. 설치 시험은 전용 일회성 runner에서 실행했습니다. 별도의 준비 runner가 같은 태그를 checkout하고 잠긴 의존성을 lifecycle script 없이 설치하여 빌드·검증·pack했습니다. 게시 job은 준비 job의 source SHA와 artifact ID를 받아 검증한 archive를 게시했으며, 배포 실행의 세 job 모두 성공했습니다.

게시 전 GitHub `npm` environment의 배포 규칙이 태그 `v*`만 허용하는 상태임을 조회·확인했습니다. 별도 required reviewer가 있다는 뜻은 아닙니다. 이번 작업에서는 로컬 npm의 Trusted Publisher 설정 목록을 새로 조회하지 않았습니다. 실제 Actions OIDC 게시 성공과 아래 인증서 identity 검증으로 이번 게시를 확인했으며, 로컬 관리자 설정을 재확인했다고 주장하지 않습니다. 워크플로에는 token secret 대체 인증이 구성되지 않았습니다.

## 파일 무결성

이번 Actions 실행의 `release-manifest.json`·실제 준비 archive와 registry에서 별도로 내려받은 archive를 비교했습니다. source SHA·태그·버전·dist-tag가 위 identity와 일치하며 SHA-256도 동일했습니다.

```text
SHA-256
b8d890b274c4c0bd14783dabe29b033c3df59fa13ca9e6f638c8ffc09e28c1e6

Registry dist.integrity (SHA-512 SRI)
sha512-/LduCLWrYrJK9ZxCXUDpD6CJnXAQjckfKTXaPHrH5b0gIKnCdqOMXhnuM1IrcdMnf4OGsZY2Fhtb44I/w8qNwA==
```

registry archive에서 계산한 SHA-512 SRI도 `dist.integrity`와 일치했습니다. 준비 단계의 로컬 후보와 digest가 같더라도 그 결과를 재사용하지 않고, 실제 배포 실행에서 생성한 artifact와 registry 파일을 새로 받아 대조했습니다.

## 서명과 provenance

`npm 11.19.1`에서 lifecycle script를 끈 격리 설치 후 `npm audit signatures --json --include-attestations`를 실행했습니다. 최종 검증에서 오류·누락이 없음을 확인하고, `verified` 배열에서 정확히 `aptly@0.1.4`에 연결된 `https://slsa.dev/provenance/v1` bundle 한 개를 확인했습니다. 종료 코드나 빈 오류 배열만으로 provenance 존재를 판단하지 않았습니다.

이 bundle과 registry archive를 `GitHub CLI 2.103.3`의 `gh attestation verify`로 검증했습니다. SHA-512, 저장소, source SHA, 태그 ref, 정확한 인증서 workflow identity를 지정하고 self-hosted runner를 거부하는 조건에서 성공했습니다. 검증된 인증서의 다음 필드를 기대값과 대조했습니다.

| 인증서 필드 | 일치한 값 |
|---|---|
| `issuer` | `https://token.actions.githubusercontent.com` |
| `sourceRepositoryURI` | `https://github.com/abruption/aptly` |
| `sourceRepositoryDigest`·`buildSignerDigest` | `85667a95693bcd083c57f857eba73ec69db1ab60` |
| `sourceRepositoryRef` | `refs/tags/v0.1.4` |
| `subjectAlternativeName`·`buildSignerURI` | `https://github.com/abruption/aptly/.github/workflows/publish.yml@refs/tags/v0.1.4` |
| `runInvocationURI` | `https://github.com/abruption/aptly/actions/runs/42203064758/attempts/1` |
| `runnerEnvironment` | `github-hosted` |

게시 성공과 provenance 검증 성공을 각각 확인했습니다. 이 결과는 해당 archive의 출처·무결성과 위 실행 identity의 연결을 확인한 것이며, 모델 품질·비용 절감이나 모든 호스트 환경의 동작을 인증하지 않습니다.

## 검증 재시도와 확인 범위

초기 버전 metadata 조회의 404 응답은 기존 실행과 registry를 읽기 전용으로 확인하며 전파를 기다렸습니다. 이와 별개로 최초 독립 검증은 격리 npm 설치 또는 서명 검증 단계에서 실패했습니다. 구체적인 npm 진단을 보존하지 못했으므로 그 실패 원인을 확정하지 않았고, registry 전파 지연으로 단정하지 않습니다. 최초 실패 이력은 최종 성공 결과와 구분해 보존했습니다.

동일 source·태그·run·attempt를 기준으로 artifact를 다시 내려받고 격리 설치·npm 서명·GitHub 인증서 검증을 재수행해 모두 통과했습니다. 게시 job을 재실행하거나 태그를 변경하거나 같은 버전을 중복 게시하지 않았으며, 이전 버전의 archive·attestation·검증 성공을 0.1.4의 근거로 사용하지 않았습니다.

이번 검증은 격리 설치를 사용했고 임시 파일을 정리했습니다. 유료 모델 API 호출, 운영 전역 설치 변경, 기존 Claude Code·Codex 설정 이전이나 자격정보 수집은 수행하지 않았습니다.

0.1.4는 상속 호출의 추천과 실제 모델 적용을 구분합니다. 제품의 상속 모델·effort 적용 차단은 유지되고, 명시적 설명 등록 API도 기본 Hook의 자동 설명 생성기를 제공하지 않습니다. 이전 구현 commit을 대상으로 한 제한된 native 시험은 [사전 라우팅 계약](../SPAWN_PREFLIGHT.md)과 [설명 전달 계약](../SPAWN_CONTEXT.md)에 별도로 기록돼 있으며, 이번 게시 검증을 모든 0.1.4 호스트의 native 적용 인증으로 해석하지 마십시오.

공개 기록에는 인증정보·신뢰 설정 ID·개인 경로를 포함하지 않습니다. 기존 영속 원장 업그레이드에는 관련 writer 중지와 [원장 잠금·오프라인 전환 안내](../LEDGER_LOCKING.md)의 확인이 필요합니다. 이 게시·검증 작업에서 실제 운영 원장을 이전하지 않았습니다.
