설치 시험은 전용 일회성 runner에서 실행했습니다. 별도의 준비 runner가 같은 태그를 checkout하고 잠긴 의존성을 lifecycle script 없이 설치하여 빌드·검증·pack했습니다. 게시 job은 그 준비 job의 source SHA와 artifact ID만 받아 검증한 archive를 게시했습니다. 세 job 모두 성공했습니다.

게시 전 npm Trusted Publisher가 `abruption/aptly`·`publish.yml`·environment `npm`에 연결되고 직접 게시가 허용된 것을 재확인했습니다. 사용자 승인으로 설정한 GitHub `npm` environment의 배포 규칙도 태그 `v*`만 허용하는 상태로 조회·확인했습니다. 이는 별도 required reviewer 설정이 있다는 뜻은 아닙니다.

## 파일 무결성

준비 artifact의 `release-manifest.json`·실제 archive와 registry에서 별도로 내려받은 archive를 비교했습니다. source SHA·태그·버전이 위 identity와 일치하며 SHA-256도 동일했습니다.

```text
SHA-256
a2fd3b3d16bf0ca7f0e48f0084378b09974b637dc362cd9d03dd97009cafd1ce

Registry dist.integrity (SHA-512 SRI)
sha512-CIBIZg+ZlSKbBaHQBoy/8K4W0eK8Ibvkp/nIOIfv46oMwylCywPnWWh1BJkEv0G9IBeDiOOonajFZxVf5X3feg==
```

registry archive에서 계산한 SHA-512 SRI도 `dist.integrity`와 일치했습니다. 실제 게시 archive는 이전 로컬 후보가 아니라 이 Actions 실행에서 생성한 artifact를 기준으로 확인했습니다.

## 서명과 provenance

`npm 11.19.1`에서 lifecycle script를 끈 격리 설치 후 `npm audit signatures --json --include-attestations`를 실행했습니다. 검증은 성공했고, `verified` 배열에서 `aptly@0.1.1`의 `https://slsa.dev/provenance/v1` bundle을 확인했습니다. 종료 코드나 빈 오류 배열만으로 provenance 존재를 판단하지 않았습니다.

이 bundle과 registry archive를 `GitHub CLI 2.103.3`의 `gh attestation verify`로 검증했습니다. SHA-512, 저장소, source SHA, 태그 ref, 정확한 인증서 workflow identity를 지정하고 self-hosted runner를 거부하는 조건에서 성공했습니다. 검증된 인증서의 다음 필드를 기대값과 대조했습니다.

| 인증서 필드 | 일치한 값 |
|---|---|
| `issuer` | `https://token.actions.githubusercontent.com` |
| `sourceRepositoryURI` | `https://github.com/abruption/aptly` |
| `sourceRepositoryDigest`·`buildSignerDigest` | `1af91644831bd709b34e1febd2318b18894dd4cb` |
| `sourceRepositoryRef` | `refs/tags/v0.1.1` |
| `subjectAlternativeName`·`buildSignerURI` | `https://github.com/abruption/aptly/.github/workflows/publish.yml@refs/tags/v0.1.1` |
| `runInvocationURI` | `https://github.com/abruption/aptly/actions/runs/42027762854/attempts/1` |
| `runnerEnvironment` | `github-hosted` |

따라서 게시 성공과 provenance 검증 성공을 각각 확인했습니다. 이 결과는 해당 archive의 출처·무결성과 위 실행 identity의 연결을 확인한 것이며, 모델 품질·비용 절감이나 모든 호스트 환경의 동작을 인증하지 않습니다.

## 확인 범위

게시 직후 registry 조회가 잠시 404를 반환했지만, 이후 같은 버전의 파일과 attestation이 제공되는 것을 확인했습니다. 전파 대기 중 게시 job을 재실행하거나 버전을 중복 게시하지 않았습니다.

검증에는 유료 모델 API 호출·전역 설치·기존 Claude Code 또는 Codex 설정 이전을 포함하지 않았습니다. 공개 기록에는 인증정보·신뢰 설정 ID·개인 경로를 포함하지 않습니다.
